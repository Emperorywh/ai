# 原型图驱动三维场景制作

目标是在既有技术和交互约束内，把参考图的主要视觉关系落实为可运行的三维场景。交付质量取决于实际画面，不取决于代码量、面数或生成资产数量。本技能来自 SC01 的实际改进与失败经验，不表示该案例已达到原型质量。

按本轮改动选择必要环节：已有可复现机位与合格几何时直接沿用，纯光照或材质修正不要求重做模型小样或新增同步工具。

## 使用入口

- 新场景：先走下方主流程，需求明确后实际制作，不只提交分析。
- 现有场景精修：从固定机位和差距诊断开始，保留已认可布局、功能及可恢复基线。
- 出现山体、积雪、植被、水光等视觉差距时，读 [视觉诊断与制作选择](references/visual-diagnosis.md)。
- 使用 Blender → Unity 或浏览器发布时，读 [资产接入与发布经验](references/blender-unity.md)。其他技术栈只采用适用原则，不迁移引擎。
- 用户需要下次直接使用的指令时，提供 [启动提示词](references/start-prompt.md)，替换其中输入，不要求额外写一份冗长需求。

## 1. 先建立制作依据

读取工程规范、需求对应章节、现有场景入口与构建方法；检查实际场景、源模型、材质、灯光和运行配置。保留锁定版本、管线、图形后端、界面语言及已有游览行为。面向本用户的菜单和提示默认简体中文，当前请求另有指定时从其指定。

确认主参考文件和用途，避免把“图2”、文件排序或航拍图误当作地面目标。有多张图时分别标注：主要构图、辅助结构、材质细节、光照气氛；不能把冲突透视拼成一个世界。图片中的人物、按钮和文字不自动增加功能。

区分三类信息：需求明确的约束、参考中可观察的关系、尚未核实的制作假设。允许在已授权的美术近似范围内推进；真实位置、高程、季节、日期或 DEM 精度必须有依据，不能由单张图推定。只在缺失信息确实影响当前决策时提问，既有授权无需重新确认。

把本轮范围和最显著的少数差距写进既有制作记录：影响画面的区域、拟改对象、验证办法。不要建立一套与现有规范冲突的新阶段体系。

## 2. 固定对照机位，再改世界尺寸

建立或沿用主参考机位并保留原游览机位。统一记录位置、朝向、坐标轴、投影类型、水平/垂直 FOV、画幅比例和默认启动视角；需要跨制作软件与引擎同步机位时，以单一配置作为依据。已有机位可靠且本轮不改时，沿用现有机制。

比较地平线、近景入口、道路转折、岸线、山峰轮廓和遮挡关系。先排除镜头位置、焦距和画幅差异，再判断道路宽度、湖面面积、山距或地形尺度。缺少可靠尺寸时记录估计，不能为像素拟合悄悄改变批准尺度。

使用同一三维世界对照，不随不同相机移动或拉伸山体，不用包含地物的整景图片冒充可探索景观。主机位接近目标后，用少量辅助视角检查接地、厚度和遮挡。

## 3. 先验证关键形体和大色块

按画面贡献选择资产方法：轮廓、厚度、遮挡和近景投影依赖几何；细微颗粒、颜色和粗糙度适合材质；连续地表、复杂岸坡、重复植被各用适合的表示。

先让主轮廓、前中远层次、林带大色块和水陆比例成立。选择最能决定画质的一小块实际资产做样段，例如一个主峰团或一段近岸路肩，直接用可编辑源资产验证制作方法。不要先批量生成整山、整岸或数千棵独立树，再发现形体或数据组织不适用。

Blender Python 可以直接建模、处理高程、生成遮罩和布置实例，但方法服从目标：重复圆锥、脊线距离函数、细分和噪声不自动产生可信山体。必要时换成雕刻、可靠 DEM、已有精修资产或混合方法；不要把一次脚本失败推导为“所有山体必须人工制作”。

## 4. 连通几何、材质和受光

先大尺度，后中尺度，最后小尺度；先结构，后纹理。小样要同时看中性形体预览与实际材质预览，防止腔隙阴影夸大细节，或用贴图掩盖错误轮廓。

统一天空亮区、主光、环境填光、雾与反射的方向和冷暖关系。水面保留底色、深浅和视角变化，反射随水波分布；不能只把整片水染成天空颜色。不要假定贴了天空图就具备 HDR 照明或山体反射。

先确定粗糙度、贴图尺度和真实色彩空间，再调后处理。核对源图实际分辨率、动态范围及全景投影；放大分辨率或抬曝光不能补回不存在的信息。

## 5. 以可判断的小循环迭代

每轮围绕一个可验证假设修改相关的一组因素，并记录观察结论。例如：“缺少前后遮挡，前移一组中景支脊”；不要同时随机改机位、地形尺寸、曝光和水色后无法归因。

制作软件先快速看形体，随后尽早将代表性模型和材质接入目标引擎；有第三方着色器或特殊后端时，在扩展前验证目标发布路径。局部无进展时检查模型方法和输入，不无限增加噪声、三角面、变体或预览次数。

遇到明确阻塞时，停止依赖该输入的工作并说明：具体画面缺陷、尝试与结果、不能继续的原因、需要的资产/数据及格式、已完成且可独立使用的部分。先判断现有授权和工具能否解决；不能只因任务困难就把建模推给用户，也不能强行用低质占位完成交付。已明确不采用的样段独立保留，不混进默认运行资产；有改善的迭代可按当前授权接入观察，但标明剩余差距并保留可恢复基线，不宣称已达最终目标。

## 6. 扩展、验证和交付

小样方法成立后才扩展。重复物体优先少量变体加共享几何/实例，按可见性和资源生命周期组织；先估算导出、下载和驻留成本，不用合并网格替代实例化。质量与性能冲突时先诊断重复数据、错误反射/阴影设置等原因；未经授权不降低核心画质或改技术栈。

遵守项目验证约束。以 SC01 约束为例，只做编译、资源/配置完整性检查、发布构建和必要运行观察，不添加单元测试或框架；其他项目按其明确规范执行。文件完整性不是视觉验收。

区分并核对状态链：制作源 → 显式导出 → 引擎导入/场景 → 发布产物 → 当前页面实际运行版本 → 用户人工视觉认可。确认当前页面加载的新产物后，才说“已经生效”；模型文件更新、编辑器预览或构建成功均不能单独证明这一点。

最后汇报实际改善、验证范围、剩余差距和可打开的结果；不能把内部观察写成用户已验收。原位更新现有文档与资产来源，保留有用制作源。临时截图、渲染预览和日志按项目要求清理；本用户未要求留存时不长期保留，不删除原型图、源纹理或运行必需文件。
